# Замкнутый цикл качества

Страница `/analytics` подключена к реальным разборам и врачебной разметке.
Редактор правил открывается по ссылке на вкладку «Триггеры» существующего дашборда.
Файл матрицы при редактировании не меняется: используется существующее версионирование в БД.

## Журнал и обезличивание

Миграция `7ab91c230def` добавляет две таблицы:

- `analysis_run`: UUID разбора, хэш ключа идемпотентности, SHA-256 текста,
  число символов, известный профиль УЗИ, время, длительность, фактический декодер,
  признак резервного декодирования, структурированные находки и решения JSON.
- `analysis_feedback`: UUID, FK разбора с каскадным удалением, триггер,
  оценка `confirmed` / `false_positive` / `missed`, время изменения.
  Уникальная пара `(analysis_id, trigger_id)` обеспечивает атомарный PUT без дублей.

Находки содержат идентификаторы соответствующих правил, хэш имени находки,
размер, уверенность и отрицание. Решения содержат срабатывание, подавление,
код причины, версию, пороги, отпечаток остальных условий, название правила,
победителя и экстренность. Название берётся из матрицы, а не из протокола.
Исходный текст, цитаты, свободные объяснения, имя файла и текст ошибки модели
в аналитике отсутствуют. Произвольный профиль исследования не сохраняется.
Пациент и его идентификаторы для этого API не нужны. Это следует принятому
подходу с `anonymized_hash`, не копируя демонстрационный external_id пациента.

SHA-256 используется для сопоставления с уже сохранёнными исследованиями;
он не объявляется гарантией невозможности восстановления известного текста.
Доступ к аналитике остаётся в рамках существующей модели доступа приложения.

Время берётся через `get_clock()`. Длительность использует монотонный счётчик
того же интерфейса: модельные часы могут стоять, а время вычисления измеряется.
Оба HTTP-эндпоинта разбора пишут журнал перед ответом об успехе.
Без заголовка каждый вызов — отдельный разбор. `Idempotency-Key` повторяет
идентификатор для того же текста и результата; изменение протокола или решения
возвращает 409 и требует нового ключа.

## Истина и формулы

`GET /api/v1/analytics/metrics` объединяет доступную gold/synthetic-разметку
с отметками врача. Разметка связывается с журналом по хэшу текста исследования.
При нескольких разборах сгенерированная метка относится к последнему по времени
разбору; при одинаковом времени UUID задаёт стабильный порядок. Отметки врача
относятся строго к указанному разбору. Для исследования без журнала выполняется
текущая оценка: она учитывается в общей метрике, но не изображается историческим
разбором и не попадает в дневной тренд. Несвязанные метки показаны отдельно.

Приоритет: отметка врача → gold → synthetic. Непроверенные пары без разметки
не считаются подтверждениями. `confirmed` и `missed` задают истинное наличие;
`false_positive` задаёт отсутствие. После изменения правила метка остаётся
фиксированной, меняется только предсказание.

- TP: наличие и срабатывание; FP: отсутствие и срабатывание.
- FN: наличие и несрабатывание; TN: отсутствие и несрабатывание.
- Recall = TP / (TP + FN); precision = TP / (TP + FP).
- Доля ошибок = (FP + FN) / (TP + FP + FN + TN).
- Доля отклонённых находок = отклонённые / (подтверждённые + отклонённые).

Пустой знаменатель даёт `null`, интерфейс пишет «недостаточно данных».
Сводка «по врачу» оценивает только врачебные отметки; общая метрика включает
остальную разметку. Усреднение выполняется суммированием матриц ошибок.
Встречаемость включает срабатывание, упоминание с отрицанием/порогом или
истинное наличие по разметке. Есть срезы по каждому правилу, профилю и дню.
Старые `/quality/*` сохранены как API оценки прежнего размеченного корпуса;
новый объединённый отчёт находится в `/analytics/metrics`.

`?current=true` сравнивает те же признаки с текущими правилами. Без изменения
условий исходное решение сохраняется. Переоценка доступна для изменений порогов
размера; новые синонимы, текстовые условия и классификации требуют повторного
разбора. Такие пары отмечаются `reanalysis_required_pairs`, а не выдают
мнимое улучшение. Исторические решения в БД не перезаписываются.
Дневной тренд показывает разные выборки по датам; сравнение на тех же
врачебных метках отдельно проверяет эффект изменения порога.

## Воспроизводимая демонстрация

В одноразовой БД после `alembic upgrade head`:

```sh
env -u PYTHONPATH -u VIRTUAL_ENV uv run python -m scripts.demo_analytics_cycle
```

Настройки PostgreSQL задаются обычными переменными `POSTGRES_*`.
Сценарий через HTTP меняет порог полипа эндометрия на 10 мм, разбирает
протоколы с размерами 12, 11, 8 и 9 мм, затем сохраняет независимые оценки врача:
подтверждено, ложная находка, пропуск, пропуск.

| Этап | TP | FP | FN | Recall | Precision |
| --- | ---: | ---: | ---: | ---: | ---: |
| До врача | — | — | — | недостаточно данных | недостаточно данных |
| После проверки | 1 | 1 | 2 | 0,333 | 0,500 |
| Порог 10 → 8 мм через редактор | 3 | 1 | 0 | 1,000 | 0,750 |

Отклонено 50% проверенных находок, или 25% всех отметок, включая пропуски.
Восемь PUT сохраняют четыре отметки; исходные решения остаются прежними.
Тест также повторяет разборы на следующий модельный день и проверяет дневной
тренд recall 0,333 → 1,000 и precision 0,500 → 0,750.

Саботаж проверен реальной временной заменой словаря врачебных отметок на пустой.
Оба теста упали: recall стал `None` вместо 1/3; при конфликте с синтетикой
precision остался 1,0 вместо 0,0. После восстановления кода тесты проходят.

Проверены HTTP API на PostgreSQL, миграции upgrade → downgrade → upgrade,
полный pytest с доступной тестовой PostgreSQL, браузер Chromium: форма разбора,
отметка врача, обновление чисел, сравнение правил и мобильная верстка.
Реальный сервер модели и нагрузочный многопользовательский сценарий не проверялись.
