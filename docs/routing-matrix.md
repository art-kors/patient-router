# Матрица маршрутизации

Матрица в `config/routing_matrix.json` собирается из двух версионируемых источников:

* `data/clinical/routing_matrix_clinician.csv` — 36 строк медицинского специалиста. Источник истины для содержащихся в нём маршрутов, SLA, приоритетов и экстренности.
* `config/routing_matrix_legacy.json` — неизменяемая исходная проектная матрица из 10 правил, полученных при разборе синтетических протоколов. Дополняет сценарии, которым нет эквивалентной замены в листе врача. Это гипотезы проекта, а не подтверждение врача.

Импорт не читает предыдущий результат: повторный запуск не накапливает правила и не меняет идентификаторы. Нет времени, случайности и хешей. Порядок — строки CSV, затем оставшиеся проектные правила в исходном порядке.

## Пополнение и запуск

Редактируйте CSV совместно с медицинским специалистом. Заголовки с русскими суффиксами обязательны; поддержаны оба написания «Подразделение»/«Подделение». Используется стандартный CSV с запятой, двойными кавычками и UTF-8. Внутренние списки синонимов/отрицаний также допускают цитированные элементы с запятыми. Фразы-доказательства делятся по `;`; запятая внутри цитаты не считается разделителем цитат. Полная исходная строка дополнительно сохраняется в `clinical_source`.

```bash
env -u PYTHONPATH -u VIRTUAL_ENV uv run python -m scripts.import_clinical_matrix
env -u PYTHONPATH -u VIRTUAL_ENV uv run python -m scripts.evaluate_extraction
```

Конвертер допускает `--csv`, `--legacy`, `--output`. При запуске непосредственно файлом: `uv run python scripts/import_clinical_matrix.py`. Валидация конфигурации выполняется приложением при старте; числовые пороги должны поддерживаться в `thresholds.py`.

Изменения через врачебный дашборд сохраняются как снимки БД и имеют приоритет над файлом. Импорт обновляет файл, но не перезаписывает существующие снимки БД. Для проверки импорта оценочный скрипт намеренно читает файл по явному пути. Изменённый в UI маршрут сохраняет происхождение базовой записи; автора конкретной редакции показывает история версий.

## Поля

| Поле | Значение |
|---|---|
| `trigger_id` | Детерминированная транслитерация полного названия для врачебных правил; прежний ID для оставленных проектных |
| `display_name` | Название находки, без сокращения составных диагнозов |
| `source_study` | Канонический тип исследования; регистр и варианты написания не создают новые типы |
| `synonyms` | Формулировки для поиска; добавлено название для сопоставления нормализованной находки словарного декодера |
| `negative_contexts` | Все отрицания врача, плюс отрицания старого правила при объединении; ничего не удаляется |
| `required_attributes` | Атрибуты врача, сохранённые списком; текущий движок не проверяет их обязательность |
| `thresholds` | Только исполняемые числовые ограничения, например `min_size_mm`, `min_stenosis_percent`, `min_birads` |
| `threshold_text` | Исходные условия врача; текст не выдаётся за исполняемый порог |
| `specialty`, `potential_route`, `department` | Специалист, возможный маршрут и координатор |
| `target_sla_days`, `priority`, `emergency_flag` | SLA в днях, приоритет 1–4 и экстренность |
| `evidence_phrases` | Список исходных фрагментов; это примеры формулировок, а не цитаты нового пациента |
| `provenance` | `clinician` — медицинский специалист; `project` — проектная гипотеза |
| `legacy_trigger_ids` | Связь с прежними категориями для аудита и сравнения метрик |
| `clinical_source` | Все 13 исходных полей CSV без потери текста |
| `version` | Редакция правила; снимки БД присваивают свою версию |

В UI у каждого правила виден источник «Врач»/«Проект», а в редакторе — исходные условия и фразы-доказательства. Происхождение и врачебные поля проходят загрузку, сохранение снимков и откат вместе с правилом.

Исходные 20 вариантов названий исследования сведены к пяти врачебным типам: малый таз, брюшная полость, артерии ног, вены ног, совместное исследование артерий и вен. Совместное исследование оставлено отдельным: при строгом сравнении типов в движке нельзя выдать его за исследование только артерий. С учётом груди и щитовидной железы в объединённой матрице семь типов.

## Решение об объединении

Всего **43 = 36 + 10 − 3** правила. Объединение задано явно в `MERGES`, а не поиском похожих слов. В пересечениях маршрут, SLA, приоритет и экстренность определяет врач; прежние синонимы и отрицания сохраняются. Прежние числовые догадки не переопределяют врача.

| Прежний ID и название | Решение |
|---|---|
| `endometrial_polyp` — Полип эндометрия | Объединён со строкой 32 «Подозрение на полип эндометрия и полип шейки матки (Показание к операции)». Сохраняется хирургическая консультация; общий старый сценарий больше не отдельное правило. Составные строки 17, 26, 34 остаются различимыми врачебными сценариями |
| `submucosal_fibroid` — Субмукозная миома матки | Оставлен отдельно: нет эквивалентного правила для субмукозной локализации и гистерорезектоскопии; проектный порог 20 мм сохранён |
| `fibroid_uterus` — Миома матки | Объединён с точным общим названием строки 31 «Миома матки». Врач назначает плановое наблюдение, приоритет 4; проектные 5 мм и хирургический маршрут удалены. Специфические сочетания с ВМС, кальцинозом, пролапсом и послеоперационным контролем не схлопываются в общую миому |
| `ovarian_cyst` — Образование яичника | Оставлен отдельно как проектный сценарий крупного образования ≥40 мм с гинекологом-онкологом. Строка 10 — параовариальная киста ORADS 2 с наблюдением; составные строки про кисты не заменяют сценарий риска |
| `breast_birads_3_5` — Образование молочной железы BI-RADS 3–5 | Оставлен: грудь отсутствует в CSV |
| `gallbladder_polyp` — Полип желчного пузыря | Оставлен: дискинезия/стеатоз из строк 35–36 не заменяют полип |
| `cholelithiasis` — Желчнокаменная болезнь | Оставлен: моторные нарушения желчного пузыря не заменяют камни/холецистит |
| `thyroid_nodule` — Узловое образование щитовидной железы | Оставлен: щитовидная железа отсутствует в CSV |
| `hydronephrosis` — Гидронефроз / конкременты | Оставлен: почечные сценарии отсутствуют в CSV |
| `lower_limb_stenosis` — Значимый стеноз артерий нижних конечностей | Объединён со строкой 5 «Признаки гемодинамически значимого атеросклероза… Окклюзия левой ЗББА». Врач: SLA 7, приоритет 2, экстренность FALSE. Старые 70%, приоритет 1 и экстренность TRUE не перенесены: врач не задаёт универсальную границу 70%. Строка 2 до 55% — другой, амбулаторный сценарий; не замена окклюзии |

CSV содержит девять строк про сосуды нижних конечностей; ещё две гинекологические строки упоминают вены малого таза. Все 36 строк сохранены. Полных дублей ID нет, но клинические признаки между составными сценариями пересекаются. Текущий движок может активировать несколько таких правил; сохранение их различий не означает взаимную исключительность срабатываний.

## Пороги и ограничения

В этом CSV **ни одно из 36 условий нельзя целиком превратить в поддерживаемый числовой порог без изменения смысла**. Конвертер поддерживает однозначные будущие формулировки «диаметр ≥ N мм», «стеноз ≥ N%». Строгое `>` не заменяется на `≥`; числовое упоминание в названии или цитате не превращается в порог.

* «диаметр БПВ > 5 мм / наличие варикозной трансформации» — альтернатива, а не обязательный размер. Числовой AND-порог потеряет пациентов с варикозной трансформацией без указанного диаметра.
* «диаметр БПВ > 5–6 мм / несостоятельность ствола / варикозные притоки» — неоднозначная граница и альтернативы.
* «окклюзия (100% стеноз) или любой значимый процент стеноза» — 100% описывает окклюзию; минимальный значимый процент врач не указал.
* «стенозы до 30%, диагноз I83.9 и повторная явка» — сочетание кода, рекомендации и степени стеноза. Один `max_stenosis_percent` не выражает правило.
* Остальные условия требуют наличия/сочетания диагнозов, морфологии, кровотока, роста, впервые установленного диагноза, послеоперационного состояния или прямого направления. Это сохранено текстом и атрибутами; автоматически движок проверяет синонимы, отрицания и только числовые `thresholds`.

**Неформализованные условия не блокируют автоматически совпадение по синониму.** Это ограничение текущего движка и причина ложных срабатываний. Импорт не означает клиническую готовность всех составных правил к автоматической маршрутизации. Нужны согласование исполняемых условий и разметка новых сценариев специалистом.

## Проверка качества

Подробные результаты и перечень всех текстовых условий: [отчёт импорта](routing-matrix-import-report.md).

Регрессионные сценарии старого процентного порога, экстренности и выбора маршрута проверяются на явно указанной неизменяемой исходной матрице. Они больше не требуют от новой врачебной редакции сохранения отвергнутых врачом порогов и экстренности. API, хранение и новые проверки импорта используют актуальные 43 правила.
