# REST API patient-router

## Статус и соглашения

> [!warning] Читайте колонку «Статус»
> В таблице ниже смешаны **реализованные ручки** и **проектный контракт**.
> Проектные ручки описаны по дизайну и ещё не написаны — вызывать их нельзя.
> Фактическое состояние всегда видно в `/docs` (Swagger) приложения.

| Статус | Значение |
|--------|----------|
| **Реализован** | Ручка работает, покрыта тестами, отвечает |
| **Реализован FastAPI** | Служебная ручка каркаса (Swagger, схема) |
| **Проектный** | Описан по требованиям кейса, кода ещё нет |

На 2026-10-03 реализовано: `GET /health`, `GET /ready`,
`POST /api/v1/analyze`, `POST /api/v1/analyze/upload`, плюс Swagger.

База целевого бизнес-API — `/api/v1`. Идентификаторы сущностей — UUID,
временные отметки — ISO 8601 с часовым поясом, даты — `YYYY-MM-DD`.
Доступ МИС предполагается сервисным, доступ врачей и координаторов — по
роли; механизм авторизации ещё не реализован.

## Реализованные служебные ответы

`GET /health`, HTTP 200, пример в модельном режиме:

```json
{
  "status": "ok",
  "app": "patient-router",
  "time": "2026-08-26T14:32:00+00:00",
  "model_clock": true
}
```

`GET /ready`, HTTP 200:

```json
{
  "status": "ready",
  "database": "up",
  "environment": "prod"
}
```

При недоступности БД — HTTP 503:

```json
{
  "status": "not_ready",
  "database": "down",
  "error": "Пример сообщения исключения соединения"
}
```

Текущее поле `error` содержит первые 200 символов исключения; это фактическое поведение, требующее фильтрации перед пилотом. `/ready` не проверяет наличие схемы или работоспособность маршрутизации.

## Контракт событий МИС

Конверт события реализован в `app/api/mis.py` (`EventIn`) вместе с
обработчиками всех 12 типов в `app/services/mis.py`. Он соответствует полям
`MisEvent`; состав `payload` задаёт проектное соглашение.

| Поле | Смысл |
|---|---|
| `event_id` | Уникальный ключ события (до 128 символов); при повторной доставке сохраняется |
| `event_type` | Один из 12 типов ниже; в ORM пока свободная строка |
| `occurred_at` | Момент фактического события МИС, с часовым поясом |
| `schema_version` | Версия конверта, для примеров — 1 |
| `patient_id` | Внутренний UUID пациента; адаптер сопоставляет внешний идентификатор |
| `study_id` | Внутренний UUID исследования; для неклинических событий может быть NULL |
| `payload` | Данные конкретного события и идентификаторы связанных объектов |

Ниже описано **действие системы**. События передают факт, а не команду назначить лечение. Все 12 типов имеют обработчики в `app/services/mis.py`.

| Тип события | Основные данные `payload` | Действие системы |
|---|---|---|
| `StudyProtocolSigned` | `protocol_id`, `study_type`, `study_date`, `signed_at`, `raw_text` | Сохранить протокол, извлечь факты, проверить правила, создать допустимый маршрут и таймеры |
| `StudyProtocolCorrected` | `protocol_id`, исправленный `raw_text`, `signed_at` | Отметить исправление, повторить оценку, согласовать существующие маршруты; отозванный триггер закрыть с `trigger_withdrawn` |
| `StudyProtocolCancelled` | `protocol_id`, причина | Отметить отмену, прекратить связанные автоматические действия, закрыть маршрут с `protocol_cancelled` |
| `AppointmentBooked` | `route_id`, `appointment_id`, `doctor_id`, `starts_at`, `slot_ref` | Зафиксировать запись, перейти в `booked`, прекратить напоминания о записи |
| `AppointmentCancelled` | `route_id`, `appointment_id`, причина | Отменить запись, вернуть необходимость записи (`booking_required`), создать соответствующие действия |
| `VisitCompleted` | `route_id`, `appointment_id`, момент завершения | Зафиксировать явку; `visit_done`, затем ожидать выбора врачебной тактики (`decision_pending`) |
| `VisitNoShow` | `route_id`, `appointment_id` | Отметить неявку (`no_show`), организовать повторный контакт и задачу координатору |
| `TacticsChosen` | `route_id`, `tactics`, врач и основание | Применить выбранную врачом тактику: направление, дообследование, наблюдение, смена профиля либо закрытие |
| `HospitalizationScheduled` | `route_id`, `hospitalization_id`, `scheduled_date` | Зафиксировать назначенную дату, перейти в `hospitalization_scheduled` |
| `HospitalizationFactual` | `route_id`, `hospitalization_id`, `actual_date` | Зафиксировать фактическое поступление, перейти в `hospitalized` |
| `SurgeryPerformed` | `hospitalization_id`, `service_code`, `performed_at` | Сохранить реально оказанную услугу, перейти в `operated`; назначенная операция фактом выполнения не считается |
| `Discharged` | `route_id`, `hospitalization_id`, момент выписки | Отметить выписку (`discharged`), организовать контроль (`followup_scheduled`) по врачебному плану |

Значения `tactics` уже определены enum `Tactics`: `surgery_indicated`, `additional_exam`, `observation`, `no_surgery`, `patient_refused`, `refer_other_specialty`. Выбор врача фиксируется в аудите; сама ORM-модель отдельного поля тактики не содержит.

### Тактика обязательна для закрытия из `decision_pending`

Требование кейса: маршрут нельзя закрыть без выбранной тактики. Из
`decision_pending` закрытие равно решению врача, поэтому `POST
/api/v1/routes/{id}/transition` в `closed_no_operation` или `closed_by_patient`
без записанной тактики отвечает **422** `TACTICS_REQUIRED` и ничего не меняет.
Проверка живёт в `RoutingService.transition`, а не в ручке, — событие МИС
`TacticsChosen` идёт через тот же сервис и не может её обойти. Тактика,
переданная в этом же переходе, считается записанной, поэтому
`POST /routes/{id}/tactics` работает как прежде.

Закрытия, где тактика по смыслу не нужна, остаются разрешёнными:

| Переход | Почему тактика не требуется |
|---|---|
| `followup_scheduled → followup_done` | Контрольный визит завершён, решение уже принималось раньше |
| `awaiting_booking → closed_by_patient` | Пациент отказался от маршрута до приёма — решения врача ещё не было |
| `notified → route_not_realized` | Маршрут не реализован: пациент недоступен, тактики нет и не могло быть |
| любой → `cancelled` | Отмена протокола или отзыв триггера — решение системы, не врача |

### Пример принятия события

Запрос `POST /api/v1/mis/events`:

```json
{
  "event_id": "mis-demo-signed-001",
  "event_type": "StudyProtocolSigned",
  "occurred_at": "2026-08-26T14:32:00Z",
  "subject": {
    "patient_id": "00000000-0000-4000-8000-000000000001",
    "study_id": "00000000-0000-4000-8000-000000000002"
  },
  "payload": {
    "study_type": "УЗИ органов малого таза",
    "study_date": "2026-08-26",
    "raw_text": "Заключение: субмукозная миома 25 мм."
  }
}
```

> [!important] Фактическая схема `EventIn`
> Идентификаторы передаются во вложенном объекте `subject`
> (`patient_id`, `study_id`, `route_id`), а не на верхнем уровне. Поля
> `schema_version` в реализованной схеме нет.

Ответ HTTP 202 — событие принято и обработано:

```json
{
  "event_id": "mis-demo-signed-001",
  "status": "processed",
  "duplicate": false,
  "route_id": "00000000-0000-4000-8000-000000000004",
  "actions": ["transition: created→notified"]
}
```

Поле `actions` перечисляет фактические действия: переходы автомата,
отклонённые переходы (`transition_rejected: …`), `route_not_found`,
`missing_study_or_patient`. Значение `status` равно `processed`, если
обработчик отработал, и `ignored`, если тип события не имеет обработчика.

Повтор того же `event_id` **с тем же содержимым** — HTTP **200** (не 202):

```json
{
  "event_id": "mis-demo-signed-001",
  "duplicate": true
}
```

Дубль не является ошибкой: это ретрай той же доставки.

Тот же `event_id` с **другим** содержимым — HTTP **409** `EVENT_ID_CONFLICT`,
и это уже ошибка. Сравниваются `event_type`, `payload`, `occurred_at` и ссылки
`subject.patient_id` / `subject.study_id`; любое расхождение означает, что
под занятым идентификатором пытаются записать другой факт. Ответ:

```json
{
  "detail": {
    "code": "EVENT_ID_CONFLICT",
    "message": "event_id mis-demo-signed-001 уже занят событием с другим содержимым. Исправление приходит новым event_id — исходный факт не перезаписывается."
  }
}
```

Событие при этом не обрабатывается, в журнал аудита ничего не пишется, а
прежняя запись остаётся в баве. Исправленный протокол МИС приходит новым
событием (`StudyProtocolCorrected` со своим `event_id`), а не перезаписью
старого. Нарушение порядка событий требует сверки связанных объектов, а не
слепого изменения состояния.

## Реализованный эндпоинт: `POST /api/v1/analyze`

Проверенный пример. Запрос:

```json
{
  "text": "ЗАКЛЮЧЕНИЕ: Эхографические признаки полипа эндометрия, 12 мм. Рекомендовано: консультация гинеколога.",
  "study_type": "УЗИ органов малого таза"
}
```

Ответ (сокращён: показаны сработавший и первые подавленные триггеры):

```json
{
  "study_type": "УЗИ органов малого таза",
  "extractor": "DictionaryExtractor(59 синонимов)",
  "conclusion_extracted": false,
  "findings": [
    {
      "finding": "Полип эндометрия",
      "organ": null,
      "laterality": null,
      "size_mm": 12.0,
      "classification": null,
      "quote": "полипа эндометрия",
      "char_start": 36,
      "char_end": 53,
      "in_negative_context": false,
      "confidence": 1.0
    }
  ],
  "matches": [
    {
      "trigger_id": "endometrial_polyp",
      "display_name": "Полип эндометрия",
      "fired": true,
      "suppressed": false,
      "suppression_reason": null,
      "quote": "полипа эндометрия",
      "confidence": 1.0,
      "applied_rule": "endometrial_polyp@v1",
      "detail": "находка найдена, отрицания нет, порог выполнен",
      "version": 1
    },
    {
      "trigger_id": "submucosal_fibroid",
      "display_name": "Субмукозная миома матки",
      "fired": false,
      "suppressed": false,
      "suppression_reason": "no_match",
      "quote": "",
      "confidence": 0.0,
      "applied_rule": "submucosal_fibroid@v1",
      "detail": "ни один синоним не встретился в тексте",
      "version": 1
    }
  ],
  "route_would_be_created": true,
  "winning_trigger": "Полип эндометрия",
  "specialty": "Оперирующий гинеколог",
  "potential_route": "Гистероскопия, гистерорезектоскопия, раздельно-диагностическое выскабливание",
  "target_sla_days": 7,
  "is_emergency": false,
  "emergency_notice": null,
  "triggered_count": 1,
  "suppressed_count": 9
}
```

Что видно в ответе и почему это важно:

| Поле | Значение для защиты |
|------|---------------------|
| `findings[].quote` | «полипа эндометрия» — дословный фрагмент, который можно подсветить врачу |
| `findings[].char_start/char_end` | Где именно в тексте: 36–53 |
| `matches[].applied_rule` | `endometrial_polyp@v1` — какое правило и какой версией |
| `matches[].detail` | «находка найдена, отрицания нет, порог выполнен» — human-readable решение |
| `matches[].suppression_reason` | `no_match` у остальных — **объяснено, почему маршрута для них нет** |
| `specialty` | «Оперирующий гинеколог» — кого вызовем |
| `target_sla_days` | 7 — целевой срок из матрицы |
| `route_would_be_created` | true — маршрут создастся; **при `is_emergency=true` всегда false** |

> [!note] Ключевое отличие
> В ответе есть решения **и для тех триггеров, которые не сработали**, с
> конкретной причиной. Без этого нельзя измерить долю ложных
> срабатываний на нормах — целевая метрика кейса ≤ 0,05.

> [!warning] Экстренная находка
> `POST /api/v1/analyze` — предпросмотр: он не меняет состояние системы.
> Но он показывает то же решение, которое применит `POST /api/v1/routes`.
> Если сработал триггер с `emergency_flag=true`, в ответе
> `is_emergency=true`, `emergency_notice` заполнен и
> `route_would_be_created=false`: **маршрут не создаётся**, персонал
> получает эскалацию. `winning_trigger` при этом остаётся заполненным —
> он объясняет, что именно сработало, но маршрута по нему не будет.

Тело запроса валидируется Pydantic: `text` — строка, `study_type` —
строка или `null`, оба необязательны (пустой протокол разбирается вхолостую).
Неверный тип поля даёт 422 с указанием поля, а не 500.

`POST /api/v1/analyze/upload` принимает файл вместо текста:
тот же контракт, поле `study_type` передаётся формой.

## Демо-эндпоинты модельного времени

Реализованы в `app/api/demo.py`. `GET /api/v1/demo/clock` возвращает
`now`, `is_mock` и `source` (`model` или `system`). Для
`POST /api/v1/demo/clock/advance` интервал передаётся **в JSON-теле**, не в
query string, и ровно одно из двух полей:

```json
{
  "days": 30
}
```

или

```json
{
  "hours": 720
}
```

Оба поля сразу или ни одного — 422 от валидатора `AdvanceIn`.

Ответ HTTP 200 — время сдвинуто, таймеры отработали:

```json
{
  "from": "2026-08-26T14:32:00+00:00",
  "to": "2026-09-25T14:32:00+00:00",
  "fired": [],
  "routes_affected": 0,
  "elapsed_ms": 12.4
}
```

`elapsed_ms` — реальная длительность обработки: 30 суток за единицы
миллисекунд. `routes_affected` — число маршрутов, чьи таймеры сработали.
`from`/`to` датированы в UTC.

Отметки `fired=true` **фиксируются в БД коммитом в ручке**, поэтому таймер
срабатывает ровно один раз: следующая прокрутка тех же 30 дней вернёт
`fired: []`. Транзакцией владеет HTTP-слой, как и обещает докстринг
`TimerEngine`; если базы нет, коммитить нечего, и в ответе
`database: "unavailable"`.

Остальные ручки группы:

| Ручка | Поведение |
|---|---|
| `POST /api/v1/demo/clock/set` | Переход к моменту `to` (обязателен часовой пояс). Откат назад — 409 `CLOCK_IN_PAST` |
| `POST /api/v1/demo/clock/reset` | Возврат к `2026-08-26T14:32:00Z` и гашение несработавших таймеров, чтобы показ можно было повторить |
| `GET /api/v1/demo/timers` | Все несработавшие таймеры маршрута. Фильтр `route_id`. Без БД — 503 `DATABASE_UNAVAILABLE` |
| `GET /api/v1/demo/scenarios` | Каталог 7 сценариев защиты: `happy_path_gynecology`, `no_booking`, `no_show`, `false_positive`, `hospitalization_stall`, `return_after_2_months`, `protocol_correction` |

Ручки часов и каталога сценариев работают **без БД**: сессия подключается
лениво с таймаутом 2 секунды и тихо отключается, если база недоступна.
`GET /demo/timers` — исключение, ему БД нужна.

Все ручки часов возвращают 409 `CLOCK_NOT_MOCK`, если `USE_MODEL_CLOCK` не
включён: модельное время включается переменной окружения, а не флагом в
запросе.

`fired` содержит эффекты, а не идентификаторы таймеров: при подключённой
БД это объекты `Effect` (`kind`, `channel`, `assignee_role`,
`template_code`, `route_id`, `timer_type`). Дальше по конвейеру эффект
должен быть передан обработчику отправки, которого пока нет.

## Оценка качества

Реализована в `app/api/quality.py`. Метрики считаются по размеченной выборке
из `LABELED_DATA_DIR` (по умолчанию `data/labeled/*.json`) и **требуют БД**:
`_evaluate()` читает `study.raw_text` сохранённых исследований и прогоняет
их через текущий экстрактор и матрицу.

Формат файла разметки — список объектов:

```json
[
  {
    "study_id": "00000000-0000-4000-8000-000000000002",
    "trigger_id": "endometrial_polyp",
    "label": true,
    "split": "gold"
  }
]
```

`label` — буквально `true` или `false` (не 1/0, не строка). `split` — либо
`gold`, либо `synthetic`; другое значение отклоняется.

| Параметр | Значение | Смысл |
|---|---|---|
| `split` | `all` (по умолчанию), `gold`, `synthetic` | Срез выборки. `all` складывает матрицы по всем исследованиям |

Форма ответа `/metrics` (значения ниже иллюстрируют **структуру**, а не
измеренный прогон; реальные числа смотрите в самом ответе):

```json
{
  "tp": 2, "fp": 0, "fn": 9, "tn": 24,
  "recall": 0.1818,
  "precision": 1.0,
  "fpr": 0.0,
  "f1": 0.3077,
  "n_samples": 35,
  "split": "all"
}
```

Значения метрик — производные от `tp`/`fp`/`fn`/`tn`; клиент их не присылает.

Считается **по паре (исследование, триггер)**: сначала каждое исследование
оценивается отдельно, затем матрицы складываются. Оценка, смешанная из
разных протоколов, дала бы неправдоподобные числа, поэтому такое смешивание
приводит к 503 `QualityScopeError`, а не к тихой порче результата.
Пустой знаменатель даёт 0, а не деление на ноль.

Это цифры **на текущем словарном экстракторе**: он находит находку по
подстроке из 59 синонимов и не понимает свободный текст. Низкий `recall`
означает, что система мало что замечает; `precision = 1.0` и `fpr = 0.0`
означают, что всё замеченное было правильным. Подробное чтение метрик — в
[README](../README.md#7-ограничения-и-что-не-сделано).

`/quality/errors` возвращает расхождения с цитатами для проверки врачом:

```json
[
  {
    "trigger_id": "submucosal_fibroid",
    "study_id": "00000000-0000-4000-8000-000000000002",
    "type": "fn",
    "label": true,
    "fired": false,
    "quote": "",
    "applied_rule": "",
    "suppression_reason": "no_match"
  }
]
```

`limit` (по умолчанию 50) ограничивает общий размер ответа.

`/quality/coverage` — единственная ручка группы, которой БД не нужна: она
сравнивает список триггеров матрицы с множеством `trigger_id` из разметки и
возвращает `total`, `covered`, `uncovered` и `ratio`. Нулевое покрытие
означает, что триггер не оценён на данных, а не что он не работает.

Разметка хакатона не публикуется (`data/labeled/` под `.gitignore`), поэтому
в свежем клоне её нет. Ручка на это отвечает HTTP **200**, а не 503:
общее число триггеров считается по `config/routing_matrix.json` и всегда
доступно, а покрытие помечается как невычислимое.

```json
{
  "total": 10,
  "covered": null,
  "uncovered": [],
  "ratio": null,
  "labeled_samples": 0,
  "available": false,
  "message": "Нет данных для оценки покрытия: каталог разметки data/labeled пуст или отсутствует. Матрица содержит 10 триггер(ов) — проверьте их через POST /api/v1/analyze."
}
```

`covered` и `ratio` равны `null`, а не `0`: ноль читался бы как «триггеры не
проверялись движком» — правдивый на вид, но неверный вывод. `available: false`
показывает, что данных для оценки нет; с разметкой ручка отдаёт
`available: true` и обычные числа покрытия.

Остальные ручки группы (`/metrics`, `/confusion`, `/errors`) без разметки
отдают 503 с текстом `QualityDataError`: там нечего считать вовсе. Тот же 503
даёт повреждённая разметка и `trigger_id`, отсутствующий в текущей матрице.

## Ошибки

| HTTP | Код / форма | Когда | Статус |
|---|---|---|---|
| 503 | `status=not_ready`, `database=down` | БД недоступна на `/ready` | Реализован |
| 404 | `detail: Not Found` | Путь отсутствует | Стандартный FastAPI |
| 405 | `detail: Method Not Allowed` | Неподдерживаемый метод существующего пути | Стандартный FastAPI |
| 422 | тело FastAPI | Неверные поля, UUID, часовой пояс, оба поля `hours`/`days` или ни одного | Реализован (формат FastAPI) |
| 409 | `CLOCK_NOT_MOCK` | Сдвиг часов при `USE_MODEL_CLOCK=false` | Реализован |
| 409 | `CLOCK_IN_PAST` | `clock/set` с моментом в прошлом | Реализован |
| 422 | `TACTICS_REQUIRED` | `POST .../tactics` без выбранной тактики, а также переход из `decision_pending` в закрытие без записанной тактики | Реализован |
| 404 | `ROUTE_NOT_FOUND` | Нет маршрута с таким `route_id` | Реализован |
| 404 | `STUDY_NOT_FOUND` | Пациент, исследование или срабатывание не найдены либо не согласованы | Реализован |
| 409 | `ROUTE_ALREADY_EXISTS` | Для срабатывания уже есть маршрут | Реализован |
| 409 | `INVALID_TRANSITION` | Переход не разрешён автоматом; в ответе `allowed_transitions` | Реализован |
| 503 | `DATABASE_UNAVAILABLE` | `GET /demo/timers` без БД | Реализован |
| 503 | текст `QualityDataError` | Нет или испорчена разметка в `LABELED_DATA_DIR` (`/metrics`, `/confusion`, `/errors`) | Реализован |
| 503 | текст `QualityScopeError` | Предсказания и разметка относятся к разным исследованиям | Реализован |
| 401 | `UNAUTHORIZED` | Нет действующей аутентификации | Проектный |
| 403 | `FORBIDDEN` | Роль не имеет доступа к клиническим данным или демо | Проектный |
| 404 | `ENTITY_NOT_FOUND` | Не найдены исследование или протокол (без маршрута) | Проектный |
| 409 | `EVENT_ID_CONFLICT` | Существующий `event_id` пришёл с другим содержимым | Реализован |
| 503 | `DEPENDENCY_UNAVAILABLE` | Недоступны МИС, расписание или доставка | Проектный |
| 500 | `INTERNAL_ERROR` | Непредвиденный сбой без раскрытия медицинских данных | Проектный |

Реализованные ошибки бизнес-API возвращаются в форме
`{"detail": {"code": "...", "message": "..."}}` — код и текст для
интерфейса. Исключения `HTTPException` модели и стандартные ошибки
FastAPI используют другую форму, `detail` без `code`.

Единая проектная форма ошибки для будущего глобального обработчика:

```json
{
  "error": {
    "code": "MODEL_CLOCK_DISABLED",
    "message": "Модельное время отключено"
  }
}
```

Она не описывает существующие `/health` и `/ready`: глобального обработчика
ошибок такой формы сейчас нет.
